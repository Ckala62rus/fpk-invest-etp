# Инструкция по пользованию ЭТП (локальная разработка)

> Для разработчика / тестировщика / демо.  
> SPA: http://localhost:5173 · API: http://localhost:8200 · MailHog: http://localhost:8025 · Horizon: http://localhost:8200/horizon · Reverb WS: `ws://localhost:6001`

**Аббревиатуры:** ЭТП (электронная торговая площадка), ТЗП (торгово-закупочная процедура), КП (коммерческое предложение), RBAC (ролевая модель доступа), ИНН (идентификационный номер налогоплательщика), ФИО (фамилия, имя, отчество).

Демо-учётки (пароль везде `password`, если не меняли `.env`):

| Роль | ИНН | Куда попадает после входа |
|------|-----|---------------------------|
| `super_admin` | `770000000000` | `/admin` |
| `trade_admin` | `770000000001` | `/admin` |
| `participant` | `770000000002` | `/cabinet` |
| `auditor` | `770000000003` | `/admin` (аудит, согласование) |

Повторный сид: `docker exec backend-etp php artisan db:seed --force`.

## 1. Гость на витрине

1. Откройте http://localhost:5173 **без входа** (или выйдите).
2. **Процедуры** — открытые ТЗП (демо: `DEMO-RFP-OPEN`, `DEMO-AUCTION-1`, `DEMO-RFP-DONE`).
3. Черновики (`DEMO-RFP-DRAFT`) и закрытые (`DEMO-RFP-CLOSED`) гостю **не** видны.
4. CMS: «О площадке», «Правила», «Контакты».
5. **Жалоба** / **Антикоррупция** → письма в MailHog.

Чтобы участвовать — **Регистрация** в шапке.

## 2. Стать участником (регистрация → одобрение)

### 2.1. Регистрация

1. `/register` — ИНН, email, пароль, профиль, согласие на ПДн.
2. Статус: `pending_email` → письмо в MailHog → подтвердите email.
3. Статус: `pending_approval` — войти в торги ещё нельзя.

### 2.2. Одобрение админом

1. `super_admin` / `trade_admin` → **Пользователи** (`/admin/users`).
2. Карточка пользователя → **Одобрить**.
3. В карточке же смотрите **документы организации** (устав и т.п.), которые участник загрузил в профиле ЛК: открыть PDF / скачать.
4. MailHog: `user_approved` → участник входит в **Кабинет**.

Демо-участник `770000000002` уже одобрен.

## 4. Как создать торги (ТЗП) и опубликовать

Два основных **типа** ТЗП:

| Тип | Зачем | Что обязательно до публикации |
|-----|--------|--------------------------------|
| **Запрос предложений** (`request_for_proposal`) | Участники подают КП (текст, файлы, ответы на поля) | Категория, заказчик, сроки; поля/условия — по желанию |
| **Аукцион** (`auction`) | Торги ставками по **лотам** | Минимум **1 лот** (цена + шаг), настройки аукциона |

Шаги:

1. Войдите `trade_admin` / `super_admin`.
2. **ТЗП** → **Создать** черновик (выберите тип).
3. На карточке заполните название, описание, даты, контакты заказчика.
4. Настройте нужные блоки (§5) → **Опубликовать**.
5. MailHog: `procedure_published` (подписчикам).
6. Витрина: процедура появляется в списке.

Демо: `DEMO-RFP-OPEN` (КП), `DEMO-AUCTION-1` (аукцион, 2 лота).

## 5. Зачем нужны кнопки на карточке ТЗП

На `/admin/procedures/:id` сверху ряд кнопок. Ниже — **зачем каждая** и **когда нажимать**.

### 5.1. КП процедуры

**Зачем:** посмотреть все коммерческие предложения по этой ТЗП, допустить/отклонить участника, вести переписку, открыть файлы КП и **документы организации** из профиля.

**Когда:** после того как участники начали подавать КП (тип «запрос предложений») или если к аукциону привязан предварительный отбор по КП.

**Как:** кнопка **«КП процедуры»** → список → глаз (карточка КП) или иконка пользователя (профиль + устав).

---

### 5.2. Лоты

**Зачем:** лот — это **отдельный предмет торгов** внутри одной аукционной ТЗП.  
Пример: одна процедура «Закупка оборудования», лот 1 — серверы, лот 2 — СХД. У каждого лота своя стартовая цена, шаг ставки, текущая цена и свой победитель.

**Когда использовать:**
- тип ТЗП = **аукцион** — лоты **обязательны** (без лота ставить некуда);
- тип «запрос КП» — лоты обычно **не нужны** (торгов ставками нет).

**Как:** кнопка **«Лоты»** → добавить лот: название, стартовая цена, шаг, единицы.  
Демо: у `DEMO-AUCTION-1` уже 2 лота.

**Важно:** участник на странице аукциона ставит **по конкретному лоту**; админ на «Управление аукционом» смотрит ставки тоже в разрезе лота.

---

### 5.3. Настраиваемые поля (custom fields)

**Зачем:** задать **анкету**, которую участник заполняет при подаче КП.  
Стандартных полей «срок поставки / гарантия / комментарий» в коде нет — вы сами решаете, что спросить.

Примеры:
- «Срок поставки, дни» (число, обязательное);
- «Наличие сертификата» (да/нет);
- «Вариант поставки» (select: самовывоз / доставка).

**Когда использовать:** почти всегда для **запроса предложений**, если нужна структурированная заявка, а не только файл.  
Для чистого аукциона без предварительного КП — можно не создавать.

**Как:**
1. Кнопка **«Настраиваемые поля»**.
2. Добавьте поле: подпись, тип (`text` / `number` / `date` / `boolean` / `select`), scope **participant**, обязательность, порядок.
3. Опубликуйте / убедитесь, что процедура в статусе приёма.
4. Участник на форме «Подать КП» увидит эти поля.

Демо: на `DEMO-RFP-OPEN` уже есть поля участника.

---

### 5.4. Доп. условия

**Зачем:** зафиксировать **особые требования процедуры** из справочника шаблонов (например: «обеспечение заявки», «электронная подпись», отраслевые условия). Это не поля формы КП, а **набор условий самой ТЗП** (метаданные закупки).

**Когда использовать:** если заказчик требует отметить стандартные условия из библиотеки площадки.

**Как:**
1. Сначала (один раз на площадке) super_admin наполняет **Шаблоны условий** `/admin/extra-conditions`.
2. На **черновике** ТЗП → **«Доп. условия»** → отметить нужные → сохранить.
3. После публикации набор обычно «заморожен» правилами статуса (правки документации идут через согласование, см. ниже).

---

### 5.5. Согласование правок

**Зачем:** после публикации нельзя «тихо» менять конкурсную документацию. Правка (например, загрузка нового файла документации) создаёт запись **change log** в статусе ожидания. Аудитор или super_admin **утверждает или отклоняет**. При утверждении срок приёма может продлиться, участникам уходит письмо.

**Когда использовать:**
- ТЗП уже **опубликована** / идёт приём;
- trade_admin загрузил новую версию документа или изменил существенные данные;
- нужен контроль (аудитор) и уведомление участников.

**Как:**
1. Trade_admin меняет документацию на опубликованной ТЗП → появляется pending change-log.
2. Войдите `auditor` (`770000000003`) или `super_admin`.
3. Карточка ТЗП → **«Согласование правок»**.
4. Approve / Reject.
5. MailHog при approve: `procedure_documentation_changed`.

На черновике согласование обычно не требуется — правьте свободно до публикации.

---

### 5.6. Внешние приглашения

**Зачем:** позвать на процедуру людей, которых **ещё нет** на площадке (или вы хотите напомнить по email). Письмо со ссылкой на витрину / регистрацию.

**Когда использовать:** закрытая или целевая закупка; рассылка подрядчикам «вне» базы участников.

**Как:**
1. На карточке ТЗП нажмите **«Внешние приглашения»**.
2. Вставьте email через запятую, `;` или с новой строки (до 500 адресов).
3. **Отправить**.
4. MailHog: шаблон `external_procedure_invite` (нужен работающий Horizon/очередь).

Это **не** то же самое, что «участники процедуры» (приглашённые зарегистрированные пользователи) и **не** допуск КП.

## 6. Подача КП (участник)

1. Участник (демо `770000000002`) → витрина → открытая процедура типа запрос предложений → **Подать КП**  
   (или из кабинета — список процедур на витрине / свои КП).
2. Заполните **настраиваемые поля** (если админ их задал).
3. Галочка **«Согласен с формой договора»** — обязательное согласие с условиями договора заказчика (файл формы договора позже подключат к документам ТЗП; без галочки API не примет КП).
4. После создания КП — кабинет **Мои КП** → текст/поля, загрузка файлов заявки, чат с админом.
5. В **Профиле** ЛК участник отдельно грузит **документы организации** (устав и т.п.) — их админ смотрит в карточке пользователя / в КП.

Админ: **КП процедуры** → открыть заявку → чат, файлы КП, документы организации, **Решение о допуске**.

## 7. После КП: допуск и что дальше

### 7.1. Решение о допуске

**Смысл:** это **не** «победитель закупки», а решение «заявка принята к дальнейшему участию / рассмотрению» или «отклонена» (с обязательной причиной).

1. Админ → КП → **Допустить** или **Отклонить** + причина.
2. Участник видит решение в карточке своего КП.

### 7.2. Связь КП и аукциона

На площадке бывают два сценария:

| Сценарий | Как жить |
|----------|----------|
| **Только запрос КП** | Создали ТЗП типа RFP → участники подали КП → допуск/отклонение → дальше работа вне аукционного тикера (выбор победителя по КП — по процессу заказчика). |
| **Аукцион** | Создали ТЗП типа **auction** → настроили **лоты** → опубликовали → при необходимости допустили участников → **Старт** аукциона → ставки. |
| **Аукцион только для допущенных с RFP** | В настройках аукциона есть флаг вроде `only_admitted_from_rfp` — тогда к торгам пускают тех, кого допустили по связанному запросу предложений. На демо смотрите настройку на странице аукциона. |

**Важно:** подача КП по `DEMO-RFP-OPEN` **сама по себе не запускает** аукцион. Аукцион — это **другая** процедура (`DEMO-AUCTION-1`) или отдельная ТЗП типа auction, которую вы создаёте сами.

## 8. Как провести аукцион (пошагово)

### Вариант А — быстро на демо

| Шаг | Кто | Действие |
|-----|-----|----------|
| 1 | Admin | `/admin/procedures` → найти **`DEMO-AUCTION-1`** → открыть |
| 2 | Admin | При необходимости **Лоты** — убедиться, что лоты есть |
| 3 | Admin | **Управление аукционом** → сохранить настройки (режим ставок, продление, победитель) → **Старт** |
| 4 | Participant | Другой браузер / инкогнито, ИНН `770000000002` → витрина или кабинет → страница аукциона этой процедуры (`/cabinet/procedures/{id}/auction`) |
| 5 | Participant | Выбрать лот → подать ставку (видит только **свои** ставки; чужие ФИО/суммы не светятся) |
| 6 | Admin | На той же странице аукциона: список ставок (с контактами), пауза / продолжить / финиш, отмена ставки, presence, протоколы |

Сидер уже допускает демо-участника к `DEMO-AUCTION-1`.

### Вариант B — свой аукцион с нуля

1. **Создать** ТЗП, тип **Аукцион**, заказчик и категория из классификатора.
2. **Лоты** — минимум один (название, старт. цена, шаг).
3. По желанию: настраиваемые поля / доп. условия / внешние приглашения.
4. **Опубликовать**.
5. Если торги только для отобранных — настройте участников / допуск / флаг «только допущенные с RFP».
6. **Управление аукционом**:
   - режим ставок / аукциона;
   - минуты продления и зона автопродления;
   - **таймаут бездействия**: сколько минут без ставок до автозакрытия; **`0` = выкл** (не закрывать из‑за простоя);
   - запрет равных ставок;
   - способ определения победителя;
7. **Старт** → участники ставят → при необходимости **Пауза** / **Финиш**.
   - На карточке ТЗП и в «Управление аукционом» виден тег фазы: **Ожидает старта** / **Идут торги** / **На паузе** / **Завершён**.
   - У участника на `/cabinet/procedures/{id}/auction` тот же тег; на паузе кнопка ставки неактивна и показано предупреждение.
8. После финиша — на **Управление аукционом** блок **«Победители по лотам»** (ИНН, организация, email) и бейдж **Победитель** в таблице ставок; PDF-протокол.
9. Участник: кабинет → **Мои аукционы** (`/cabinet/auctions`) — список торгов и бейдж **Вы победитель**; на странице аукциона — тот же алерт по выигранным лотам.

### Таймаут бездействия (инструкция)

Автозавершение торгов без кнопки «Финиш» бывает по двум причинам:

| Причина | Когда | Как отключить / ослабить |
|---------|--------|---------------------------|
| **Простой (бездействие)** | Нет ставок дольше N минут (`idle_timeout_minutes`, по умолчанию 30) | В **Управление аукционом** поставьте **Таймаут бездействия = 0** и **Сохранить настройки** |
| **Срок окончания** | Наступило `ends_at` процедуры | Сдвиньте дату окончания на карточке ТЗП (пока даты ещё можно менять) |

**Как выключить простой на демо:**

1. Откройте процедуру-аукцион (черновик или «ожидает аукциона» — **до Старта**).
2. **Управление аукционом / ставки**.
3. Поле **«Таймаут бездействия, минут»** → **`0`**.
4. **Сохранить настройки**.
5. Дальше **Старт**. Торги не закроются из‑за паузы в ставках; закрытие — по **Финиш** или по дате окончания.

**Важно:**

- Настройки аукциона меняются только **до начала торгов** (черновик / ожидание аукциона). Уже завершённую ТЗП заново «открыть» нельзя — для теста создайте новую или используйте демо.
- На **паузе** автозавершение по простою тоже не срабатывает.
- `0` не отключает закрытие по **`ends_at`**.

В журнале активности: `auction_finished_idle` (простой), `auction_finished_deadline` (срок), `auction_finished` (ручной Финиш).

### Что видит участник vs админ

| | Участник | Админ |
|--|----------|-------|
| Текущая цена лота | да (тикер) | да |
| Свои ставки | да | да (все) |
| Чужие ставки / ФИО / email | **нет** | да |
| Свой статус победителя | да («Мои аукционы» + страница аукциона) | да (таблица победителей + бейдж в ставках) |
| Отмена ставки | нет | да (+ письмо `bid_cancelled`) |
| Presence (кто онлайн) | нет | да |

## 9. Realtime (Reverb / Echo)

Чтобы ставка обновлялась **без F5**:

1. `backend/src/.env`: `BROADCAST_CONNECTION=reverb` + блок `REVERB_*`.
2. `frontend/.env`: `VITE_REVERB_ENABLED=true`, `VITE_REVERB_APP_KEY` = тот же, что `REVERB_APP_KEY`, host `localhost`, port `6001`.
3. Контейнер `reverb-etp` слушает **6001**.
4. Перезапустить Vite после смены `.env`.
5. В DevTools → Network → WS: соединение к `ws://localhost:6001`.

События: `BidPlaced`, `AuctionExtended`, `AuctionStateChanged`, `BidCancelled`.  
Без Reverb: `BROADCAST_CONNECTION=verifying_log` и лог `etp.broadcast` — см. [09-websocket-how-to.md](./09-websocket-how-to.md).

## 10. Аудит и письма

### Аудит

1. `auditor` / `super_admin` → `/admin/activity`.
2. Фильтры, детали JSON, экспорт CSV.

### MailHog — шпаргалка

| Событие | Код шаблона |
|---------|-------------|
| Одобрение пользователя | `user_approved` |
| Публикация ТЗП | `procedure_published` |
| Внешнее приглашение | `external_procedure_invite` |
| Новое КП (админам) | `proposal_submitted` |
| Отмена ставки | `bid_cancelled` |
| Смена документации | `procedure_documentation_changed` |
| Напоминания / инвайты аукциона | `auction_reminder_*`, `auction_invite_*` |
| Опрос качества | `evaluation_survey` |

Шаблоны: `/admin/notifications`. Очереди: Horizon.

## 11. Быстрый чеклист «с нуля за 15 минут»

1. Гость → процедуры видны.
2. Регистрация → MailHog → approve в Пользователях (проверить документы профиля).
3. Участник подаёт КП на `DEMO-RFP-OPEN` → админ допускает в КП.
4. Admin стартует **`DEMO-AUCTION-1`** → участник ставит по лоту → тикер (Reverb).
5. По желанию: внешние приглашения → MailHog; правка документации → согласование аудитором.
6. `/admin/activity` — записи publish / bid / approve.

## Частые вопросы

**«Я подал КП — где аукцион?»**  
КП и аукцион — разные типы процедур (или связанные этапы). Откройте/создайте ТЗП типа **auction**, добавьте **лоты**, нажмите **Управление аукционом → Старт**. Демо-аукцион: `DEMO-AUCTION-1`.

**«Зачем лоты, если одна закупка?»**  
Даже при одном предмете в аукционе нужен минимум один лот — это «корзина» для цены и ставок. Несколько лотов = несколько независимых торгов в одной процедуре.

**«Зачем настраиваемые поля?»**  
Чтобы собрать от участника нужные ответы в форме КП без доработки кода.

**«Зачем доп. условия?»**  
Чтобы повесить на ТЗП стандартные условия из справочника площадки.

**«Зачем согласование правок?»**  
Чтобы смена документации после публикации проходила контроль и уведомляла участников.

**«Зачем внешние приглашения?»**  
Чтобы разослать email тем, кого ещё нет в системе (или нужно точечно позвать).
